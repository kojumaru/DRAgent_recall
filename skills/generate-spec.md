# /spec-gen — 部品正常仕様書の対話的生成

## 概要

`agent.py` の自律ループとは異なり、このスキルは **Claude とユーザーの対話** によって仕様書を作る。
各セクションでユーザーが確認・修正を入れながら進めるため、品質と根拠を都度担保できる。

出力: `dataset/specs/{recall_id}/spec_FTA.md`（クリーンな仕様本文 ＋ HTML コメント形式の情報源）

---

## Step 0 — 入力の解決

`$ARGUMENTS` に recall_id が渡された場合はそれを使う。
渡されなかった場合は `data/` 配下のディレクトリを列挙し、ユーザーに選ばせる。

以下のパスを順に探す（存在する最初のものを使う）:
- `data/{recall_id}/raw.json`
- `../fta-spec-generator/dataset/recalls/{recall_id}/raw.json`  ← fta-spec-generator 側にある場合

ファイルが見つからなければユーザーに正しいパスを確認する。

### 改善箇所説明図（diagram PDF）の読み込み

raw.json の `diagram_pdf_url` を確認する。

**キャッシュ済みの場合（優先）**: `data/{recall_id}/diagram.pdf` が存在すれば Read する。

**未キャッシュの場合**: `diagram_pdf_url` の URL から Python でダウンロードして `data/{recall_id}/diagram.pdf` に保存後、Read する:
```python
import urllib.request, shutil
req = urllib.request.Request(url, headers={'User-Agent': 'Mozilla/5.0'})
with urllib.request.urlopen(req, timeout=30) as r, open(out_path, 'wb') as f:
    shutil.copyfileobj(r, f)
```

図面から以下を読み取り、仕様書生成に使用する:
- 部品の設置位置・取付構造（周辺部材との位置関係）
- 接合方式（溶接形状・締結方法）
- 改善前後の差分（構造上の正常状態を裏付ける情報として使用する）

`diagram_pdf_url` が null または図面が存在しない場合はスキップする。

## Step 1 — リコール内容の提示と対象部品の確認

raw.json を Read して以下を表示する:

```
【リコール概要】
届出番号  : {recall_id}
届出者    : {notifier}
対象車種  : {affected_vehicles[0].maker} {affected_vehicles[0].model}
不具合部位: {defect_location}
不具合系統: {defect_system}
部品リスト: {parts[].part_name}
不具合概要: {defect_summary}（仕様書本文には使わない）
```

ユーザーに確認: **「仕様書の対象部品をこれでよいですか？ 別の部品にする場合は教えてください。」**

ユーザーの回答を受け取り、対象部品名（`product_name`）を確定する。

---

## Step 2 — 部品カテゴリのトリアージと調査計画

確定した対象部品を以下のカテゴリに分類し、優先する情報源を決定する。

### 部品カテゴリ別 調査優先マップ

| カテゴリ | 判定基準 | 最優先情報源 | 次点情報源 |
|---|---|---|---|
| **OBD・診断系** | ECU/車載式故障診断装置/OBD/スキャンツール/診断通信 | 保安基準第17条の二 → ISO 15031（OBD）→ SAE J1979（PID定義） | UN-R OBD / 国交省細目告示 |
| **電気・電子系** | センサ/スイッチ/ECU/ハーネス/コネクタ | 保安基準（電気装置関連条文）→ ISO 26262 → UN-R | JIS D / J-PlatPat |
| **機械・構造系** | ボルト/ブラケット/シャフト/ギア/スプリング | JIS B / JIS D → 保安基準 → J-PlatPat | J-STAGE |
| **流体・密封系** | ホース/パイプ/バルブ/シール/パッキン/グロメット | JIS B / JIS D → 保安基準 → J-PlatPat | UN-R（ブレーキ液等）|
| **制動・操舵系** | ブレーキ部品/ステアリング/サスペンション | 保安基準（制動/操舵条文）→ UN-R13/R79 → JIS | J-PlatPat |
| **照明・信号系** | ランプ/リフレクタ/ウィンカー | 保安基準（灯火条文）→ UN-R48 → JIS C | J-PlatPat |
| **動力・駆動系** | エンジン部品/トランスミッション/モータ | 保安基準（排出ガス等）→ UN-R83/R49 → JIS | J-STAGE |

分類結果とともに「調査を開始します」とユーザーに伝えて Step 3 に進む（承認不要）。

**情報源の共通優先順位（カテゴリにかかわらず）:**
1. 機械工学事典 (JSME) — 原理・構造の基礎知識
2. 道路運送車両の保安基準 (e-Gov)
3. UN規則 (UNECE) / ISO規格
4. JIS規格 (JISC)
5. 特許情報 (J-PlatPat)
6. 論文 (J-STAGE)
7. その他（メーカー公式等、上記で不足する場合のみ）

---

## Step 3 — 一括調査と仕様書生成

セクション 1〜7 を**一括で**調査・執筆する。ユーザーへの確認は行わない。

### 調査手順

**最初に必ず機械工学事典で対象部品を検索する:**
- 検索クエリ例: `site:jsme.or.jp/jsme-medwiki {部品名}`
- 事典に記載があれば、原理・構造・機能の基礎をそこから取得する

その後、Step 2 のトリアージ結果に従って優先情報源を調査する:
- 保安基準: `web_fetch("https://laws.e-gov.go.jp/law/326M50000800067")`
- UNECE UN規則: `web_fetch("https://unece.org/transport/vehicle-regulations")`
- 検索クエリ例: `{部品名} JIS規格`, `{部品名} UN規則 要件`, `{部品名} ISO 26262`, `{部品名} ISO 16750`, `{部品名} 特許 動作原理`
- **section 7 では特に** 以下を調査する:
  - OBD・診断系部品（ECU/車載式故障診断装置）の場合:
    `web_fetch("https://laws.e-gov.go.jp/law/326M50000800067")` → 保安基準第17条の二（車載式故障診断装置）条文を取得する
    `web_search('ISO 15031-5 SAE J1979 OBD PID calculated engine load service 01')`
    → ISO 15031-5 / SAE J1979 の対象 PID の定義式・正常値範囲・単位を取得する
    **Section 5（出力仕様）には不具合に関連する PID の正常値を必ず記述する。**
    表は使わず箇条書きで記述する。特定の運転状態（エンジン停止・暖機中・全開等）における具体的な数値を明示する。
    曖昧な表現（「正しく表示される」「適切な値を返す」等）は使わず、「エンジン停止時（回転数 0 rpm）は 0%」のように状態と数値をセットで書く。
  - 電気電子系部品（ECU/センサ/スイッチ/ハーネス）の場合:
    `web_search('ISO 16750 vehicle electrical environmental conditions temperature vibration')`
    → ISO 16750-2（電源変動: 動作電圧範囲・過電圧耐性）・16750-4（振動: 加速度・周波数範囲）・16750-5（温度: 動作温度範囲）から具体的な数値を取得する
    `web_search('ISO 26262 automotive functional safety ASIL {部品カテゴリ名}')`
    → ASIL要求レベルと関連する設計要件（診断カバレッジ・フォールトトレランス時間等）を取得する
  - 機械系部品の場合:
    e-Gov 保安基準の該当条文で取付強度・材質要件を確認する
- ブログ・個人サイト・ECサイトは使わない
- URL直接fetchで取得できない場合は、別クエリで web_search して別URLから再試行する
  （例: `{部品名} ISO 16750 要件`、`{部品名} UN-R {規則番号} requirements`）
- 複数試行後も情報が得られない場合は、同種部品の一般的な工学知識・業界標準に基づいて
  推論した内容を記述し、必ず `<!-- [AI推論] {推論の根拠説明}。 -->` コメントを付ける
  （「記載なし」は絶対に書かない。省略もしない。必ず推論で埋める）
  - コメント内に「専門家確認要」「要確認」「未確認」等の語句を入れない。根拠の説明だけを書く

調査完了後、以下の形式で完全な spec_FTA.md を一括生成して Step 4 へ進む。

```markdown
# 部品正常仕様書

対象部品：{product_name}

## 1. 対象部品の特定
{確認済みの内容}
<!-- [出典] ... -->

## 2. システム内での役割
{確認済みの内容}
<!-- [出典] ... -->

## 3. 構成・関連部品
{確認済みの内容}
<!-- [出典] ... -->

## 4. 入力仕様
{確認済みの内容}

## 5. 出力仕様
{確認済みの内容}

## 6. 正常動作シーケンス
{確認済みの内容}

## 7. 使用環境・要求条件
{確認済みの内容}
<!-- [出典] ... -->
```

**禁止事項（保存前チェック）:**
- リコール原因・不具合状態・故障モード・改善措置が本文に混入していないか確認する
- 情報源括弧書き `（...）` が本文テキストに残っていないか確認する
- `## 参照情報源` テーブルを spec_FTA.md に含めない
- **仕様書本文（セクション 1〜7）にマークダウンの表（`|---|`形式）を使わない。** 列挙は箇条書き（`-`）で表現する
- 「要確認」「専門家確認要」「〜を確認する必要がある」等の不確実性・確認依頼を示す語句を本文・HTMLコメントのいずれにも含めない（仕様書は「現状どうなのかを調べる必要がある」ではなく「正常時はこうである」と断言するドキュメント。確認できなかった項目はAI推論で埋めてコメントには推論の根拠のみを書く）

確認後、即座に Step 4 へ進む（ユーザーへの確認は不要）。

---

## Step 4 — ファイル保存

以下を Write する:
- `data/{recall_id}/spec_FTA.md`

`data/{recall_id}/` が存在しない場合は作成してから保存する。

保存完了後:
```
保存しました:
  data/{recall_id}/spec_FTA.md

次のステップ:
  ビューワーで仕様書を確認・レビューしてください。
  その後 /extract-label と /convert-input を実行してください。
```

## 情報源の付け方ルール

| OK | NG |
|----|-----|
| `- 〇〇の機能を担う` ← 本文はクリーン | `- 〇〇の機能を担う（保安基準第△条）` ← 括弧書きNG |
| `<!-- [出典] e-Gov 保安基準 https://... 第△条 -->` | `## 参照情報源` テーブルを spec に書く |
| 情報が得られなかった項目は一般知識で推論して `<!-- [AI推論] 根拠。 -->` を付ける | 「記載なし」と書く・項目を省略する |

## セクション定義（参考）

| # | セクション名 | 主な記述内容 |
|---|------------|------------|
| 1 | 対象部品の特定 | 部品名・設置位置のみ |
| 2 | システム内での役割 | 上位システムにおける機能・用途 |
| 3 | 構成・関連部品 | 周辺部品・接続関係（部品名：機能説明の形式） |
| 4 | 入力仕様 | 電気的・機械的・通信的入力の形式・条件 |
| 5 | 出力仕様 | 出力信号形式・出力先 |
| 6 | 正常動作シーケンス | 起動→通常動作→停止の時系列 |
| 7 | 使用環境・要求条件 | 温度・振動・電源・法規要件等（日本保安基準 + UNECE UN規則 + ISO 16750/ISO 26262） |
