# /generate-spec — 部品正常仕様書の対話的生成

## 概要

`agent.py` の自律ループとは異なり、このスキルは **Claude とユーザーの対話** によって仕様書を作る。
各セクションでユーザーが確認・修正を入れながら進めるため、品質と根拠を都度担保できる。

出力: `data/{recall_id}/spec_FTA.md`（クリーンな仕様本文 ＋ HTML コメント形式の情報源）

---

## Step 0 — 入力の解決

`$ARGUMENTS` に recall_id が渡された場合はそれを使う。
渡されなかった場合は `data/` 配下のディレクトリを列挙し、ユーザーに選ばせる。

以下のパスを順に探す（存在する最初のものを使う）:
- `data/{recall_id}/raw.json`

ファイルが見つからなければユーザーに正しいパスを確認する。

### 改善箇所説明図（diagram PDF）の読み込み

raw.json の `diagram_pdf_url` を確認する。

**キャッシュ済みの場合（優先）**: `data/{recall_id}/diagram.pdf` が存在すれば Read する。

**未キャッシュの場合**: `diagram_pdf_url` の URL から Python でダウンロードして `data/{recall_id}/diagram.pdf` に保存後、Read する:
```python
import urllib.request, shutil
req = urllib.request.Request(url, headers={'User-Agent': 'Mozilla/5.0'})
with urllib.request.urlopen(req, timeout=30) as r, open(out_path, 'wb') as f:
    shutil.copyfileobj(r, f)
```

図面から以下を読み取り、仕様書生成に使用する:
- 部品の設置位置・取付構造（周辺部材との位置関係）
- 接合方式（溶接形状・締結方法）
- 改善前後の差分（構造上の正常状態を裏付ける情報として使用する）

`diagram_pdf_url` が null または図面が存在しない場合はスキップする。

---

## Step 1 — リコール内容の提示と対象部品の確認

raw.json を Read して以下を表示する:

```
【リコール概要】
届出番号  : {recall_id}
届出者    : {notifier}
対象車種  : {affected_vehicles[0].maker} {affected_vehicles[0].model}
不具合部位: {defect_location}
不具合系統: {defect_system}
部品リスト: {parts[].part_name}
不具合概要: {defect_summary}（仕様書本文には使わない）
```

ユーザーに確認: **「仕様書の対象部品をこれでよいですか？ 別の部品にする場合は教えてください。」**

ユーザーの回答を受け取り、対象部品名（`product_name`）を確定する。

---

## Step 2 — 部品タイプの判定と調査計画

確定した対象部品を以下の4タイプに分類する。

### 部品タイプ定義

| タイプ | 判定基準 | 例 |
|---|---|---|
| **A: 信号処理・制御系** | 信号・データを入力として受け取り、演算・制御した結果を出力する | ECU、センサ、スイッチ、制御基板、OBD装置 |
| **B: 流体系** | 液体・気体を通過・制御させることが主機能 | ホース、パイプ、バルブ、逆止弁、ブレーキシリンダ |
| **C: 機械・構造系** | 力・荷重・トルクを受けながら形状・位置を保持することが主機能 | ボルト、シャフト、ブラケット、スプリング、軸受、ギア |
| **D: 素材・接合系** | 材料特性によって光学・気密・接着・断熱等の性能を発揮する | ガラス、接着剤、プライマー、シール、パッキン、グロメット |

### 棄却条件

上記4タイプのいずれにも明確に分類できない場合（例: 設計プロセス・作業手順・ソフトウェア単体・リコール原因が部品の問題でなく手順書の誤りである場合等）は、**このリコールの仕様書生成を棄却する**。

```
【棄却】{recall_id}
理由: 対象部品「{product_name}」はA〜Dのいずれの部品タイプにも分類できません。
  → 仕様書生成をスキップします。
  → 別のrecall_idを選択するか、対象部品を変更してください。
```

### 調査優先情報源（タイプ共通）

1. 道路運送車両の保安基準 (e-Gov)
2. UN規則 (UNECE) / ISO規格
3. JIS規格 (JISC)
4. 特許情報 (J-PlatPat)
5. 論文 (J-STAGE)
6. その他（メーカー公式等、上記で不足する場合のみ）

### タイプ別優先情報源

| タイプ | 最優先情報源 |
|---|---|
| A: 信号処理・制御系 | 保安基準第17条の二（OBD系）、ISO 26262、ISO 15031、SAE J1979、ISO 16750 |
| B: 流体系 | JIS B / JIS D、保安基準（制動・燃料系条文）、UN-R13 |
| C: 機械・構造系 | JIS B / JIS D、保安基準（強度・取付要件）、J-PlatPat |
| D: 素材・接合系 | JIS R（ガラス）、JIS A（接着・シーリング）、JIS K（接着剤）、保安基準 |

分類結果を表示して「調査を開始します」とユーザーに伝え、Step 3 に進む（ユーザー承認不要）。

---

## Step 3 — 一括調査と仕様書生成

セクション 1〜7 を**一括で**調査・執筆する。ユーザーへの確認は行わない。

### 調査手順

Step 2 のタイプ分類とトリアージに従って優先情報源を調査する:
- 保安基準: `web_fetch("https://laws.e-gov.go.jp/law/326M50000800067")`
- UNECE UN規則: `web_fetch("https://unece.org/transport/vehicle-regulations")`
- URL直接fetchで取得できない場合は web_search で別URLから再試行する
- 複数試行後も情報が得られない場合は、同種部品の工学知識・業界標準に基づいて推論し `<!-- [AI推論] {推論の根拠説明}。 -->` を付ける
  （「記載なし」は絶対に書かない。コメント内に「要確認」「専門家確認要」等は入れない）

### セクション 1〜3・7（全タイプ共通）

```markdown
## 1. 対象部品の特定
{部品名・設置位置のみ。取付構造（周辺部材との位置関係）を含む}

## 2. システム内での役割
{上位システムにおける機能・用途。1〜3文で簡潔に}

## 3. 構成・関連部品
{対象部品と直接インターフェースする部品のみ。3〜5件。内部部品の細かい列挙はしない}
- {部品名}：{対象部品との接続関係・役割}

## 7. 使用環境・要求条件
{温度・振動・電源・法規要件等}
```

### セクション 4〜6（タイプ別に切り替え）

---

#### タイプ A: 信号処理・制御系

```markdown
## 4. 入力仕様
{使用中に受信する信号・電源の形式・条件（電圧範囲・通信プロトコル・センサ入力値域等）}

## 5. 出力仕様
{出力する信号・制御値の形式と正常範囲（具体的な数値・単位で記述。曖昧な表現は使わない）}
<!-- OBD・診断系の場合: ISO 15031-5 / SAE J1979の対象PIDの定義式・正常値範囲・単位を必ず記述する -->

## 6. 正常動作シーケンス
{起動→通常動作→停止の時系列。使用中の動作を記述する（製造・施工プロセスは書かない）}
```

---

#### タイプ B: 流体系

```markdown
## 4. 入力条件
{使用中に受ける流体の圧力・温度・流量・流体種別（液体/気体）の入力条件}

## 5. 出力仕様
{下流へ供給する流量・圧力の正常範囲。正常時の通過量・遮断性能等を具体的数値で記述}

## 6. 正常動作シーケンス
{弁開閉・圧力調整・流路切替等の動作シーケンス。使用中の動作を記述する（製造プロセスは書かない）}
```

---

#### タイプ C: 機械・構造系

```markdown
## 4. 作用荷重条件
{使用中に受ける力・トルク・振動の大きさ・方向・周波数（走行荷重・締結トルク・衝撃荷重等）}

## 5. 強度・変形要件
{変形・脱落・折損しないために満たすべき仕様値（降伏強度・締結トルク規定値・疲労寿命等）}

## 6. 正常保持状態
{荷重を受けながら構造的完全性を保っている状態の記述。「変形せず位置を維持する」「規定トルクで締結され緩みが生じない」等}
```

---

#### タイプ D: 素材・接合系

```markdown
## 4. 作用環境入力
{施工完了後の使用中に受ける環境入力（熱・振動・水・紫外線・化学物質等の条件と強度）}
<!-- 施工・製造条件（塗布量・養生時間等）は記載しない。使用中の環境入力のみ記述する -->

## 5. 機能・性能要件
{施工完了後に発揮すべき性能値（接着強度・光線透過率・気密性・耐熱温度等）。JIS・ISO等の規格値を使う}

## 6. 正常保持状態
{環境入力を受けながら性能を維持している状態の記述。「経年後も接着強度を維持する」「振動下で気密性を保持する」等}
<!-- 製造・施工手順は記載しない。使用中に正常に機能している状態のみ記述する -->
```

---

### 禁止事項（保存前チェック）

- リコール原因・不具合状態・故障モード・改善措置が本文に混入していないか確認する
- 情報源括弧書き `（...）` が本文テキストに残っていないか確認する
- `## 参照情報源` テーブルを spec_FTA.md に含めない
- **仕様書本文（セクション 1〜7）にマークダウンの表（`|---|`形式）を使わない。** 列挙は箇条書き（`-`）で表現する
- 「要確認」「専門家確認要」「〜を確認する必要がある」等の語句を本文・HTMLコメントのいずれにも含めない
- タイプ D のセクション 4・6 に製造・施工条件・施工手順を含めない

確認後、即座に Step 4 へ進む（ユーザーへの確認は不要）。

---

## Step 4 — ファイル保存

以下を Write する:
- `data/{recall_id}/spec_FTA.md`

`data/{recall_id}/` が存在しない場合は作成してから保存する。

保存完了後:
```
保存しました:
  data/{recall_id}/spec_FTA.md
  部品タイプ: {A/B/C/D} — {タイプ名}

次のステップ:
  ビューワーで仕様書を確認・レビューしてください。
  その後 /generate-label と /generate-input を実行してください。
```

## 情報源の付け方ルール

| OK | NG |
|----|-----|
| `- 〇〇の機能を担う` ← 本文はクリーン | `- 〇〇の機能を担う（保安基準第△条）` ← 括弧書きNG |
| `<!-- [出典] e-Gov 保安基準 https://... 第△条 -->` | `## 参照情報源` テーブルを spec に書く |
| 情報が得られなかった項目は一般知識で推論して `<!-- [AI推論] 根拠。 -->` を付ける | 「記載なし」と書く・項目を省略する |

|---|---|---|
| 1 | 対象部品の特定 | 部品名・設置位置・取付構造 |

| 6 | ※タイプ別 | A/B: 正常動作シーケンス / C/D: 正常保持状態 |
