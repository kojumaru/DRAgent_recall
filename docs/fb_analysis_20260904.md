## 3. スキル改善案

### 3.1 generate-spec.md への改善案

#### 【最優先】P1: 数値の使用禁止
**問題**: sec4（作用荷重条件）・sec5（強度・変形要件）・sec7（使用環境・要求条件）に具体的な数値（温度範囲、耐久回数、電流値、圧力値等）を記載しているが、根拠のある数値を断定できない。

**現状の出力例**:
- 「周囲温度：−30〜120℃（エンジンルーム内）」
- 「規定耐久回数（数万回以上）」
- 「数百Aの大電流」

**改善案**: 数値を記載する際は必ず「〜程度」「〜以上（詳細は設計仕様書を参照）」に留め、断定的な数値は`[AI推論]`コメントを付けることを必須化する。もしくは、sec4/5/7では数値を一切使わず定性的な表現のみを許可する。

```
【追加ルール】
- sec4, sec5, sec7 に具体的な数値（温度値, 電流値, 荷重値, 耐久回数）を記載しない
- どうしても数値が必要な場合は「（詳細は設計仕様書参照）」と付記する
- 単位を伴う数値はすべて<!-- [AI推論] -->コメント内にのみ記載
```

#### P5/P6: sec4・sec6の内容制限
**問題**: sec4「作用荷重条件」に製造条件（接着手順、焼付け温度等）が混入。sec6「正常保持状態」に製造手順が混入。

**改善案**:
```
【sec4 作用荷重条件】
- 記載するのは使用中に作用する荷重のみ（走行荷重, 熱, 振動, 電流等）
- 製造条件・製造温度・組付け条件は記載しない

【sec6 正常保持状態】
- 部品が使用中に正常に機能している状態を記載する
- 製造手順・組付け工程は記載しない（「〜が正しく施工されている状態」等はNG）
```

#### P7: sec3の関連部品を絞る
**改善案**:
```
【sec3 構成・関連部品】
- 対象部品と直接物理的・電気的に接続する部品のみ記載（最大5〜7点）
- 間接的に関係する上位システム（ECU全般、バッテリー等）の羅列は避ける
```

#### P8: 保安基準引用の扱い
**改善案**:
```
【sec2・sec7 保安基準引用】
- 保安基準の条項番号は必ず<!-- [AI推論] -->内に記載する
- 誤った引用を避けるため、具体的な条項番号の記載は任意（確信がある場合のみ）
```

### 3.2 generate-label.md への改善案

#### 【最優先】P2: 「〜機能を喪失する」表現の禁止
**問題**: 故障モードとして「〇〇が××機能を喪失する」という抽象的表現が多数。専門家から「破損する/損傷する/折損する」の方が理解しやすいと繰り返し指摘。

**現状の出力例**:
- 「アッパーアームシャフトが構造保持機能を喪失する」→ 「破損する」
- 「ブレーキパイプが流体密封機能を喪失する」→ 「破損する」
- 「カメラレンズが光学透過機能を喪失する」→ 「損傷する」
- 「テーパースプライン嵌合部が固定機能を喪失する」→ 「緩む/外れる」

**改善案**:
```
【禁止表現】
- 「〜機能を喪失する」「〜機能が失われる」「〜機能が低下する」はすべて禁止
- 代わりに具体的な物理変化動詞を使う:
  機械部品: 折損する / 破断する / 亀裂が発生する / 変形する / 摩耗する / 緩む / 脱落する
  電気・電子: 短絡する / 断線する / 腐食する / 誤検知する / 誤演算する
  流体系: 漏れる / 詰まる / 膨潤する / 破損する
  素材系: 膨潤する / 剥離する / 劣化する / 損傷する
```

#### P3: 初期状態記述の禁止
**問題**: 「〜が適切に固定されていない」「〜の強度が不足している」「〜が誤って書き込まれている」など、製造初期の不適切な状態を故障モードとして記述している。

**改善案**:
```
【禁止表現】
- 「〜されていない」「〜が不足している」「〜が誤っている」（形容詞・状態表現）はNG
- 故障モードは必ず動詞（変化・事象）で終わること
- 初期不良は製造原因であり、それ自体は故障モードではない（causal_chainの先頭に入れる）
```

#### P4: カスケード事象の混入防止
**問題**: 故障モードに、直接の故障結果（カスケード事象）が含まれている。

**現状の例**（005659 ルームランプ）:
- 「ルームランプの取付爪が折損する」← これが故障モード（OK）
- 「ルームランプが脱落する」← カスケード事象（NG）
- 「ルームランプ金属部がキャビン本体に接触してショートする」← さらなるカスケード（NG）

**改善案**:
```
【ルール】
- 故障モードは対象部品自体に起きる直接的な物理変化のみ
- 故障モードの結果として起きる後続事象（脱落、接触、発火等）はcausal_chainに記載
- 故障モードが2つ以上の場合、互いに「原因→結果」の関係になっていないか確認する
```

#### P9: トップ事象から状況説明を除去
**問題**: 「走行中に走行不能となる」→「走行不能となる」のように、トップ事象に発生状況（「走行中に」「使用時に」）が混入。

**改善案**:
```
【top_event のルール】
- 状況説明（「走行中に」「エンジン始動時に」「使用を続けると」等）を含めない
- 結果のみを記述する: 「走行不能となる」「火災に至る」「保安基準に適合しない」
```

#### P10: 制御プログラム起因の不具合の扱い
**問題**: コントロールユニットの制御プログラムが原因の不具合で、部品（ユニット）として表現すると「プログラムが悪い」という点が表現できない。

**改善案**:
```
【制御プログラム起因の場合】
- target_component に「〜コントロールユニット」を含める
- failure_modes に「制御プログラムが〜する（誤検知する / 誤演算する / 不適切な制御をする）」を含める
- missing_items（故障モードとして挙げ忘れた観点）として「制御プログラム設定不備」を検討する
```
